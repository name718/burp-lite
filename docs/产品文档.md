# Chaos-Proxy 产品需求文档 (PRD)

**项目名称**：Chaos-Proxy（混沌代理）  
**文档版本**：V1.0  
**目标用户**：前端开发工程师、测试工程师、全栈开发人员  
**核心价值**：**零侵入、零配置、实时篡改**——在不修改前端代码的前提下，模拟极端网络环境与后端异常响应。

---

## 1. 项目背景与愿景

### 1.1 痛点分析

- **联调依赖**：前端调试异常页面（如支付失败、超时、500错误）需要后端配合造数据，沟通成本高。
- **环境固化**：代码中的 `BaseURL` 写死，无法随意切换到测试环境或 Mock 环境。
- **难以复现**：线上偶发的慢接口、数据乱码、连接断开等问题，在本地极难复现。
- **性能盲区**：无法精准预判弱网或高并发下前端页面的实际表现。

### 1.2 产品愿景

打造一个轻量级的本地代理调试“外挂”。通过拦截浏览器发出的所有 HTTP(S) 请求，按预设规则注入**延迟、错误码、篡改响应体**，帮助前端团队在无需后端支持的情况下，全面测试应用的容错性与健壮性。

## 3. 核心功能模块（MVP 阶段）

### 3.1 透明代理转发

- **功能描述**：启动后监听本地端口（如 `8888`），浏览器或系统代理指向该端口后，所有请求被透传到目标服务器。
- **技术约束**：**初始版本仅支持 HTTP**（HTTPS 因涉及中间人证书，复杂度较高，暂定为 V2.0 目标）。
- **性能指标**：代理转发额外耗时 < 5ms，不影响正常请求体验。

### 3.2 故障注入引擎（核心）

通过本地 `rules.json` 文件定义规则，支持以下故障类型：

1.  **响应延迟 (Latency)**：
    - 配置：`delay: 3000`（毫秒）。
    - 效果：代理收到后端响应后，等待指定毫秒数再将数据转发给浏览器。
2.  **状态码篡改 (Status Code)**：
    - 配置：`status_code: 500`。
    - 效果：无论后端返回什么，一律强制重写响应行状态码。
3.  **响应体篡改 (Body Manipulation)**：
    - 配置：`find: '"code":0'`, `replace: '"code":10001'`。
    - 效果：字符串替换，用于模拟业务错误码。
4.  **连接中断 (Connection Drop)**：
    - 配置：`action: "close_immediately"`。
    - 效果：在接收到请求后（或接收到部分响应后）直接关闭 Socket，模拟网络闪断。

### 3.3 规则匹配器

规则需要精准命中目标，避免误伤其他请求（如静态资源 CSS/JS）。

- **匹配维度**：
  - `url`：支持前缀匹配（如 `/api/`）或精确匹配。
  - `method`：GET / POST / PUT 等。
  - `header`：可选，如仅匹配包含特定 `x-request-id` 的请求。

### 3.4 运行日志与监控

- **终端实时输出**：彩色打印请求路径、匹配到的规则、注入的故障、耗时。
- **统计摘要**：退出时打印命中规则总数、成功转发数、注入故障数。

## 4. 配置规范 (rules.json)

开发阶段以文件配置为主，未来 UI 界面将直接生成此 JSON。

```json
[
  {
    "name": "模拟登录接口系统繁忙",
    "enabled": true,
    "match": {
      "url": "/api/user/login",
      "method": "POST"
    },
    "inject": {
      "delay_ms": 2000,
      "status_code": 503,
      "body_modify": {
        "find": "\"success\":true",
        "replace": "\"success\":false,\"msg\":\"系统繁忙，请稍后重试\""
      }
    }
  },
  {
    "name": "订单列表慢查询",
    "enabled": true,
    "match": {
      "url": "/api/order/list"
    },
    "inject": {
      "delay_ms": 5000
    }
  }
]
```

> **特别约定**：为避免乱码，代理转发时会强制移除请求头中的 `Accept-Encoding`（即强制后端返回明文），确保 Body 替换操作有效。

## 5. 用户交互流程

### 命令行工具 (CLI) 操作流程

1. 前端同学下载编译好的二进制文件 `chaos-proxy`。
2. 在项目根目录创建 `rules.json` 并写入规则。
3. 终端执行 `./chaos-proxy -p 8888 -c ./rules.json`。
4. 将系统代理设置为 `127.0.0.1:8888`（或使用 SwitchyOmega 等插件）。
5. 刷新浏览器页面，终端实时显示拦截日志。
6. 修改 `rules.json` 后无需重启，工具自动检测文件变更并热加载（`inotify` 或定时轮询）。

## 6. 非功能性需求

| 指标         | 目标值                                                     |
| :----------- | :--------------------------------------------------------- |
| **性能**     | 单进程支持 100+ 并发连接，CPU 占用 < 5%（单核）。          |
| **内存占用** | 运行时内存占用 < 20MB（不含大文件缓存）。                  |
| **体积**     | 编译后二进制文件 < 5MB。                                   |
| **兼容性**   | 支持 macOS (Darwin) 和 Linux (amd64)，初期不支持 Windows。 |
| **语言约束** | 全 C 语言开发，依赖最小化（仅依赖 POSIX 标准库）。         |

## 7. 产品路线图

### V1.0 - 核心引擎 (当前迭代)

- [x] 基于 `epoll`/`select` 的 HTTP 代理基础转发。
- [x] 强制解压（删除 gzip 请求头）。
- [x] 配置文件（JSON）解析与热加载。
- [x] 延迟注入 + 状态码篡改 + 基础字符串替换。
- [x] 彩色终端日志。

### V2.0 - 易用性与协议扩展

- [ ] 支持 HTTPS (MITM，基于 `mbedtls` 或 `OpenSSL`)。
- [ ] 支持 WebSocket 消息拦截与篡改。
- [ ] 提供基于 HTML + CSS 的本地 Web UI（通过内嵌 RESTful API 管理规则），替代手写 JSON。

### V3.0 - 团队协作

- [ ] 支持规则导出/分享（链接或文件）。
- [ ] 支持从远程 URL 拉取公共 Mock 规则集。

## 8. 附：UI 界面设计草案（V2.0 规划）

针对您之前提出的“UI是否必要”，V2.0 的 UI 将直接嵌入二进制文件，前端无需额外安装环境。

- **技术选型**：C 语言内嵌 `libmicrohttpd` 提供 Web 服务，前端界面使用原生 HTML/CSS/JS（无框架），**单页应用**。
- **页面布局**：
  - **左侧列表**：展示当前所有规则，支持启用/禁用开关。
  - **右侧详情**：点击规则后，展示可编辑的表单（URL匹配、延迟滑块、状态码下拉框）。
  - **底部日志流**：自动滚动显示实时代理日志（类似 `tail -f`）。
